Движок AJAX-фильтрации каталога через HTML-атрибуты pf-* в разметке темы — товары WooCommerce, любой другой тип записи или блог, любое число независимых профилей фильтра.

== Description ==

PF Filter не диктует внешний вид карточек, сетки или фильтров — вся разметка остаётся полностью на стороне темы/верстальщика. Плагин находит разметку по HTML-атрибутам `pf-*`, строит фасетный фильтр, запускает AJAX-запросы к собственному REST API и обновляет список записей, счётчики, пагинацию и активные фильтры без перезагрузки страницы.

**Любой тип записи.** WooCommerce не обязателен: если он активен, товары фильтруются со всеми своими особенностями (атрибуты, наличие, цена, скидка); если нет — плагин работает с любым типом записи сайта (в т.ч. блогом или кастомным CPT) и его таксономиями.

**Профили фильтра.** Настройки — не один набор на весь сайт, а список независимых профилей: у каждого свой тип записи, группы фильтров, пагинация, сортировка. `pf-profile="id"` в разметке — одновременно и выбор профиля, и граница блока фильтрации, поэтому на одной странице можно разместить несколько независимых блоков (например, маленький фильтр услуг и маленький фильтр новостей на главной странице сайта), не мешая друг другу.

**Шаблоны групп фильтра:** чекбоксы, радио, теги, дропдаун (чекбоксы/радио), дерево категорий (для любой иерархической таксономии, с ограничением глубины — действует и на плоских шаблонах, не только на дереве), диапазон/слайдер (для цены, любого числового ACF-поля записи, любое количество независимых range-групп сразу — например «Цена» и «Вес»), наличие товара (для WooCommerce).

**Диапазон/слайдер:** перетаскивание бегунков, ввод значения напрямую числом (с подсказкой текущей границы, пока сторону не тронули), полоска подсветки между бегунками — всё через pf-* атрибуты, без готового CSS от плагина.

**Сортировка:** по умолчанию, по дате (в обе стороны), для WooCommerce — по цене/популярности/рейтингу/размеру скидки, плюс по любому ACF-полю записи и по названию значения любого атрибута/таксономии — для любого типа записи.

**Первая загрузка страницы** рендерится обычным WordPress-loop — плагин не вмешивается в первичный рендер. AJAX-обновления сами находят настоящий PHP-файл, которым тема рендерит карточку (архив, произвольная страница со встроенным блоком, включая главную), и воспроизводят разметку карточки один в один — без ручного создания шаблонов карточки для плагина.

**Диагностика.** Отдельная вкладка в настройках — проверка окружения сервера, разметки конкретной страницы каталога и собственных REST-эндпоинтов, без сохранения между запусками.

Полное описание атрибутов, REST API и структуры конфигурации — см. REFERENCE.md в репозитории проекта.

== Installation ==

1. Загрузите папку `pf-filter` в `/wp-content/plugins/`.
2. Активируйте плагин через меню «Плагины» в WordPress.
3. На странице Настройки → PF Filter создайте профиль (или используйте профиль по умолчанию), выберите тип записи и настройте группы фильтров и сортировку.
4. Разметьте страницу каталога атрибутами `pf-form`, `pf-target` (если форм/списков на странице несколько), `pf-list`, `pf-output`, `pf-templates`, `pf-profile` (если профилей на сайте несколько или блоков фильтрации на странице несколько) и т.д.

Теперь номер страницы записывается в URL только на настоящих архивных страницах; на встроенных блоках пагинация продолжает работать кликами как обычно, просто не сохраняется при перезагрузке страницы.

= 1.8.4 =
* Критическое исправление, устраняет корневую причину, которую 1.8.2/1.8.3 лечили частично: при двух и более одновременных range-группах (например «Цена» и «Вес») они могли взаимно блокировать друг друга — третий фильтр временно схлопывал ОБЕ группы до "0..0" (0 подходящих записей), это схлопнутое значение уходило на сервер КАК БУДТО реальный выбор пользователя в обеих группах сразу, и даже после снятия того третьего фильтра каждая range-группа продолжала обнулять результат другой своим искусственным "0"-фильтром — взаимная блокировка без выхода. Причина: на сервер отправлялось отображаемое (визуально подстроенное под остальные фильтры) значение слайдера, а не исходный выбор пользователя.
* Теперь это две принципиально разные вещи: отображение слайдера по-прежнему подстраивается под остальные активные фильтры (в т.ч. может честно схлопнуться в 0, если сейчас ничего не пересекается — это нормально, чисто визуальная подсказка), а на сервер как фактическое условие всегда уходит "замороженный" исходный выбор пользователя (data-user-min/data-user-max), независимо от того, что в моменте показывает слайдер. Не тронутая пользователем сторона диапазона (только "от" либо только "до") корректно уходит без ограничения, а не искусственным нулём.
* Чипы активных фильтров для range-групп больше не зависят от текущих (плавающих) границ трека — раньше чип мог пропадать/появляться из-за изменения СОСЕДНЕЙ, никак не связанной range-группы.

= 1.8.3 =
* Критическое исправление, продолжение 1.8.2 (тот фикс оказался неполным): при активном range-фильтре и одновременном сужении/расширении границ трека другими фильтрами (авто-подстройка из 1.5.5/1.8.0) выбор пользователя мог "залипать" в схлопнутой (сузившейся до одной точки) позиции и не расширяться обратно даже после того, как границы трека честно раздвигались снятием другого фильтра — потому что подстройка клэмпила уже возможно суженное текущее значение, а не исходный выбор пользователя. Проявлялось на страницах с несколькими одновременными range-группами особенно заметно (например, "Старая цена" оставалась зажатой в одной точке после сброса фильтра категории, хотя её собственные границы уже вернулись к полным).
* Теперь min и max каждого ползунка хранят "замороженное" абсолютное значение выбора пользователя независимо друг от друга (data-user-min/data-user-max, выставляются только реальным drag/клавишами/числовым полем) — при каждой авто-подстройке границ именно это исходное значение обрезается по новым min/max, а не уже потенциально суженное текущее. Диапазон теперь корректно "возвращается" к исходному выбору пользователя при снятии других фильтров, вместо того чтобы оставаться зажатым в промежуточном сужении.

= 1.8.2 =
* Критическое исправление: у range-группы (цена и любое другое такое поле) авто-подстройка границ трека под остальные активные фильтры (см. 1.5.5/1.8.0) определяла "тронул ли пользователь ползунок" сравнением текущего выбора со старыми границами трека — если границы схлопывались в одну точку (например, при другом активном фильтре остался ровно один подходящий товар), это сравнение давало ложный результат: диапазон считался "нетронутым" и на следующем обновлении границ сбрасывался, даже если пользователь его реально выбрал. Внешне это выглядело как: снятие/добавление ДРУГОГО фильтра "откатывало" range-фильтр визуально (и в чипах активных фильтров), хотя на самом деле он оставался в запросе к серверу; после перезагрузки страницы с диапазоном в URL ползунок сбрасывался на значения по умолчанию; при двух одновременных range-группах они могли портить состояние друг друга.
* Теперь "тронут ли пользователем" определяется напрямую флагом data-user-adjusted (выставляется только реальным drag/клавишами/числовым полем), а не сравнением значений — устраняет весь класс описанных выше симптомов.

= 1.8.1 =
* Исправлено: в списке доступных полей группы шаблон range можно было выбрать для товарного атрибута (таксономии) или кастомного/локального атрибута с числовыми значениями (например, атрибут «Длина» со значениями 100/200/300) — ползунок в этом случае всегда показывал 0..0, потому что у терминов/атрибутов нет постоянного numeric-поля, откуда диапазон мог бы взять реальные границы. range теперь предлагается только для настоящих числовых meta/ACF-полей (см. 1.8.0), для таксономий/custom_-атрибутов — как и раньше, чекбоксы/радио/теги/дропдауны.
* Уже сохранённые на сайте группы с такой (нерабочей) комбинацией поле+range самовосстанавливаются: ответ /config для них теперь возвращает корректный шаблон (checkbox) автоматически, без необходимости вручную открывать и пересохранять настройки.

= 1.8.0 =
* Новое: «Цена» перестала быть отдельной захардкоженной сущностью — теперь это обычная range-группа по числовому meta-полю записи. Список доступных полей для range-группы пополняется любыми ACF-полями, зарегистрированными на настроенный тип записи (по аналогии с уже существующим автоподбором ACF-полей для цвета термина) — можно построить, например, диапазон «Вес» или «Стоимость услуги» без единого товара WooCommerce.
* Для уже сохранённых на сайте групп с полем `price` ничего не меняется — это по-прежнему синоним meta-ключа `_price`, обратная совместимость сохранена.
* Можно настроить сразу несколько независимых range-групп одновременно (например «Цена» и «Вес») — раньше числовой диапазон был жёстко один на весь фильтр.
* JS-движок фильтра обобщён: подстройка границ ползунка под остальные активные фильтры, чипы активных фильтров, кнопка сброса группы и сохранение диапазона в URL страницы теперь работают для ЛЮБОЙ range-группы, а не только для поля с именем `price`.
* Попутно исправлен обнаруженный в этом же месте код баг: диапазон, восстановленный из URL страницы (`?price_min=...&price_max=...`) при перезагрузке визуально позиционировал ползунок правильно, но не передавался в запрос к серверу — итоговый список не был по нему отфильтрован.

= 1.7.1 =
* Исправлено: выпадашка «Тип записи» показывала медиафайлы и страницы (WordPress регистрирует их public=true, но каталогом с фильтром их не листают) — теперь эти два типа записи из списка исключены.
* Исправлено: атрибуты WooCommerce (например «Цвет»), у которых не включена настройка «Enable Archives?» (Товары → Атрибуты) — таких большинство — пропадали из списка доступных полей группы при типе записи product. Причина: список полей стал строиться по register_taxonomy()'s public=false у таких атрибутов (там это отражает именно «Enable Archives?», а не «показывать ли в фильтре»). Теперь атрибуты pa_* допускаются в список независимо от этого флага.
* Исправлено: кастомные/локальные атрибуты товаров (_product_attributes) и «Цена» — всё ещё жёстко WooCommerce-специфика (см. ROADMAP.md, этап 3) — показывались в списке доступных полей для ЛЮБОГО типа записи, включая блог и кастомные типы без единого товара. Теперь показываются только когда настроенный тип записи — product.

* Новое: настройка «Тип записи» на странице Настройки → PF Filter — плагин может фильтровать любой публичный тип записи сайта (в т.ч. кастомный), не только товары WooCommerce. По умолчанию — product, если WooCommerce активен, иначе post.
* Новое: список доступных полей для группы фильтра теперь строится из ВСЕХ публичных таксономий выбранного типа записи (get_object_taxonomies()), а не только из атрибутов WooCommerce — для блога это, например, «Рубрики» и «Метки».

* Убраны спецкейсы под product_cat/product_tag/pa_* в построении запроса и списка групп — любая таксономия обрабатывается одинаково.
* Диагностика и предупреждение «реальная глубина дерева больше настроенной» теперь считаются по таксономии конкретной группы (было — одно глобальное предупреждение только для категорий товаров) и показываются прямо в таблице групп фильтров.
* Известное ограничение (см. ROADMAP.md): авто-сужение счётчиков/видимости групп по «активной категории» в /config всё ещё жёстко привязано к product_cat — для остальных типов записи и таксономий пока не активируется.

= 1.6.0 =
* Новое: WooCommerce больше не обязателен для активации и работы плагина — все вызовы WooCommerce-функций обёрнуты проверками, плагин деградирует до обычного WordPress-рендера, если WooCommerce не активен (первый этап перехода на универсальный движок, см. ROADMAP.md проекта).
* Рендер карточки без WooCommerce: если извлечь шаблон карточки из PHP-файла страницы не удалось, плагин пробует стандартную WordPress-конвенцию темы (content-{тип записи}.php / content.php), а если и её нет — рендерит минимальную карточку (заголовок-ссылка + эксцерпт), чтобы AJAX-ответ не оставался пустым.
* pre_get_posts-хук, ограничивающий posts_per_page главного запроса каталога, обобщён — больше не хардкодит post_type=product, а также ограничивает главный запрос блога (is_home()), если плагин настроен на тип записи post.
* Диагностика: проверка «WooCommerce активен» теперь ошибка только если плагин настроен на тип записи product; для остальных типов записи — информационное предупреждение, а не ошибка.
* Из заголовка плагина убран `WC requires at least` — WooCommerce больше не жёсткая зависимость.

= 1.5.9 =
* Новое: цвет значения атрибута/категории (для [pf-filter-swatch]) теперь берётся из поля ACF/term meta термина — в настройках группы выпадашка «Цвета» сама находит поля, привязанные (через правила локации) к таксономии этого поля (acf_get_field_groups()/acf_get_fields(), только если ACF активен), достаточно выбрать нужное. Значение читается напрямую через get_term_meta(), без формальной зависимости от функций ACF — сработает и с term meta без ACF вообще. Работает только для реальных таксономий (pa_*, product_cat) — у кастомных атрибутов термов не существует.
* Убран ручной ввод цвета (slug → hex) — теперь единственный источник цвета термина это выбор поля ACF/term meta.

= 1.5.8 =
* Критическое исправление: после снятия любого фильтра (чекбокс, метка, категория и т.п.) список товаров и счётчик могли остаться неверными («залипшая» фильтрация), если до этого границы цены автоматически сузились под тот фильтр (например, у выбранного цвета в наличии только один товар по одной цене). Причина — collectFilters() всегда отправлял текущий диапазон цены как активный фильтр, даже когда это было чисто визуальное автоподстроенное значение, а не выбор пользователя; после снятия другого фильтра суженная цена продолжала «приклеенной» лететь в запрос и реально фильтровала товары.
* Ползунок цены теперь помечается data-user-adjusted только реальным действием пользователя (drag/клавиши/числовое поле) — автоматическая подстройка границ под другие активные фильтры (см. 1.5.5) этот флаг не трогает. Фильтр price отправляется на сервер только если флаг стоит; сброс группы/всех фильтров его снимает.

= 1.5.7 =
* Исправлено: при схлопнувшемся диапазоне цены (min === max — очень узкий диапазон или один товар) оба ползунка накладывались друг на друга в одной точке (0%), не различить и не за что зацепиться. Теперь в этом случае min-ползунок раскладывается на 0%, max — на 100%, оба остаются на виду.
* [pf-filter-remove] теперь скрыт по умолчанию — виден только когда у этой конкретной группы реально есть активный фильтр (как и [pf-active-reset]).
* Критическое исправление: клик на [pf-filter-remove] визуально сбрасывал фильтр и пересчитывал счётчики, но список товаров обновлялся только после второго клика (заметно на пагинации в режиме both/load-more/infinite). Причина — forceReplace/silent были общими полями на инстансе, выставлялись в момент вызова runFilter(), но читались в handleResponse() асинхронно в момент ответа; если между вызовом и ответом успевал выполниться другой runFilter() (например, отложенный rangeDebounced), ответ читал уже перезаписанные чужие флаги. Теперь эти флаги передаются per-request явно вместе с ответом, а не через общее состояние.

= 1.5.6 =
* Критическое исправление регрессии 1.5.5: границы ползунка цены схлопывались в цену одного товара (data-min == data-max) уже при первой загрузке страницы, дальше ломая фильтрацию по всем остальным запросам. Причина — PF_Query::build() прогонял posts_per_page через absint(), которая отбрасывает знак: -1 (конвенция WordPress "без ограничения", так вызывает count_price_bounds(), чтобы посчитать реальный min/max по всем подходящим товарам) превращался в 1 — запрос молча ограничивался одним товаром. Раньше баг был спящим, клиент counts.price просто игнорировал; проявился сразу после того, как в 1.5.5 подключилась подстройка границ.

= 1.5.5 =
* Новое: ползунок цены теперь подстраивает границы трека (не только текущий выбор) под остальные активные фильтры — точно так же, как уже подстраиваются счётчики у остальных групп. Сервер это уже считал (counts.price), клиент раньше данные игнорировал. Если ползунок ещё не трогали — граница "едет" вместе с новыми доступными min/max; если уже выбран поддиапазон — он обрезается по новым границам, а не сбрасывается.
* Новое: атрибут [pf-filter-remove] — необязательная кнопка сброса фильтра конкретно одной группы (в отличие от [pf-active-reset], сбрасывающего все фильтры разом), может быть где угодно внутри pf-template, работает одинаково для любого шаблона группы.
* Новое: страница настроек предупреждает ⚠, если для включённой настройки в реальной вёрстке нет нужного элемента — "Показывать счётчик товаров" (нет [pf-filter-count]), вкладка "Сортировка" (нет [pf-sort]), группа → "Поиск" (нет текстового поля в шаблоне), группа → "Цвета" (нет [pf-filter-swatch] в шаблоне).
* Исправлено: при сбросе диапазона цены (Сбросить все фильтры / кнопка сброса группы) ползунок возвращался в позицию без центрирования (левый край на 0%/100% вместо центра) — не использовал фикс центрирования из 1.5.3.
* Внутренний рефакторинг: resetGroupFilter() раньше сбрасывал только range-группы (использовался лишь чипом цены) — для checkbox/radio/tags/category-tree ничего не делал. Общая логика сброса вынесена в resetGroupControls(), теперь работает для всех типов групп (нужно было для [pf-filter-remove]).

= 1.5.4 =
* Критическое исправление регрессии 1.5.3: поиск внутри группы фильтра (в т.ч. по категориям) переставал работать вообще. Причина — reinitWebflow() вызывал общий Webflow.destroy()+Webflow.ready(), который перезапускает ВСЕ модули Webflow разом, включая "forms" — тот управляет той же <form>, что и pf-form, и его переинициализация ломала обработчик поля поиска.
* reinitWebflow() переписан точечно: вместо общего destroy()+ready() теперь вызывается только Webflow.require('dropdown').ready() (безопасно вызывать повторно — модуль сам снимает старые обработчики перед новыми) и Webflow.require('ix2').init(). Модуль "forms" (и другие, отвечающие за не относящуюся к дропдаунам функциональность) больше не трогается.
* Дополнительная защита: обработчик поиска внутри группы теперь навешивается делегированно на весь узел группы, а не напрямую на поле ввода — устойчиво к любой переинициализации поля сторонним JS темы, не только Webflow.

= 1.5.3 =
* Исправлено: ползунок диапазона цены визуально вылезал за пределы трека справа. positionHandle() ставил только left:X% (левый край ползунка), без компенсации его собственной ширины — на 100% ползунок неизбежно вылезал наружу. Добавлен transform: translateX(-50%), теперь ползунок центрируется на своей позиции.
* Исправлено: вложенные категории не находились при поиске по дереву категорий. Строка-родитель со своим pf-hidden визуально скрывала всех потомков (display:none у предка перекрывает детей), даже если у самого совпавшего потомка pf-hidden был снят. Строка теперь видна, если совпала она сама, либо любой её потомок/предок в цепочке.
* Исправлено: «Сбросить все фильтры» не снимал визуальное выделение с активной радиокнопки. У Webflow-виджета радио «визуально отмечен» — отдельный CSS-класс (w--redirected-checked) на соседнем элементе, управляемый только по клику на конкретный input; кликом принципиально нельзя выразить «сними выбор со всех» (радио — это всегда «выбери этот один»). Теперь при программном снятии класс убирается явно.
* Исправлено: вложенные дропдауны дерева категорий не раскрывались по клику после того, как их строил плагин (хотя в самой теме, без плагина, работали). Причина — Webflow инициализирует свои дропдауны один раз при загрузке страницы, а дерево категорий строится позже, асинхронно после ответа /config, поэтому клонированные узлы дерева Webflow просто не видел при своей инициализации (в отличие от групп верхнего уровня, тут нельзя один раз «переместить» оригинал — категорий на одном уровне обычно несколько). Добавлен вызов Webflow.destroy()/Webflow.ready()/require('ix2').init() сразу после построения групп — просит сам Webflow пересканировать DOM и переинициализировать свои дропдауны/анимации как есть, никакой собственной логики раскрытия плагин не реализует. На сайтах без Webflow (window.Webflow не существует) — no-op.

= 1.5.2 =
* Исправлено: переход по ссылке в каноничном для WordPress формате пагинации `/page/N/` (например `/shop/page/3/?price_min=...`) открывал страницу 1 вместо N. Плагин читал номер страницы только из query-строки (`?paged=N`, в этом формате он сам пишет URL), но не из сегмента пути `/page/N/`, в котором отдаёт ссылки сам WordPress/тема. Теперь читается и то, и другое; `updateUrl()` при этом убирает сегмент `/page/N/` из пути, чтобы не задваивать номер страницы одновременно в пути и в query-строке.
* Исправлено: группы фильтра, нерелевантные текущей выборке (например, после выбора категории, где ни у одного товара нет значений по этому атрибуту), не скрывались автоматически — оставались видны со старыми значениями. Сервер уже пересчитывал релевантность на каждый AJAX-запрос (авто-релевантность по категории и по остальным активным фильтрам), но клиент использовал это только для обновления цифр счётчиков, не для показа/скрытия самой группы.
* Исправлено: клик по строке-тегу (шаблон tags, в т.ч. плоский список категорий) и ещё несколько кликов внутри формы (сортировка, «Загрузить ещё», «Сбросить все фильтры», удаление чипа активного фильтра) не вызывали preventDefault. Если верстальщик использовал для такого элемента `<button>` (тип по умолчанию submit), клик реально отправлял [pf-form] как обычную HTML-форму — на Webflow-сайтах это показывало служебную ошибку самого Webflow вида «Ошибка отправки! Формы не настроены». Добавлена и точечная защита в каждом обработчике, и общий preventDefault на submit самой формы (она никогда не должна отправляться нативно).
* Исправлено: пагинация по страницам (одинокая кнопка «1») не скрывалась, когда весь результат умещается на одну страницу — теперь блок номеров страниц скрывается целиком, если страница всего одна.
* Исправлено: в таблице групп фильтров содержимое ячеек «Range: шаг/ед.», «Дерево: глубина», «Цвета» съезжало под чужие заголовки. Причина — CSS скрывал неприменимые к шаблону ячейки через `display:none`, а у разных строк скрыт разный набор из этих ячеек, из-за чего оставшиеся видимые в каждой строке сдвигались на разное число столбцов. Заменено на `visibility:hidden` — ячейка остаётся зарезервированным столбцом, выравнивание больше не ломается.
* Новое: настройка «Сортировка значений» для каждой группы фильтра — по алфавиту (А→Я/Я→А) или по количеству товаров (по возрастанию/убыванию). Работает для любого типа группы со списком значений (таксономия, кастомный атрибут, плоские категории, дерево категорий — там сортировка применяется на каждом уровне отдельно).

= 1.4.1 =
* Критическое исправление: сайт (админка и фронт) полностью белел после обновления до 1.4.0. Причина — в class-pf-card-template.php однострочный комментарий содержал буквальный текст `<?php ... ?>`; PHP обрывает такой комментарий на первом `?>` и переходит в текстовый режим, а последующий `<?php` в файле включал PHP обратно посреди обычного текста комментария — из-за этого весь код в файле дальше по тексту не парсился (`Parse error: syntax error, unexpected identifier`). Комментарий переписан без буквальных PHP-тегов внутри. Ошибка воспроизведена и исправление подтверждено реальным PHP-линтером (php -l) на PHP 8.5, а не подсчётом скобок вручную.

* Новое: автоматическое извлечение шаблона карточки товара прямо из PHP-файла страницы каталога (PF_Card_Template) — без ручного создания content-product.php и без каких-либо pf-* атрибутов внутри карточки.
  Плагин находит PHP-файл, которым тема рендерит конкретную страницу (кастомный page template или переопределение архива WooCommerce), вырезает из него тело цикла товаров внутри [pf-list] (код между the_post() и endwhile) и подключает его один раз на каждый товар при AJAX-фильтрации — включая условные блоки темы (бейджи, атрибуты и т.п. отрабатывают их же собственной логикой, а не угадыванием).
  Результат кэшируется в wp-content/uploads/pf-filter-cache и пересчитывается автоматически при изменении файла темы. При любой ошибке извлечения/выполнения — тихий откат на прежний wc_get_template_part('content','product').
