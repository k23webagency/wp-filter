Движок AJAX-фильтрации каталога WooCommerce, работающий через HTML-атрибуты pf-* в разметке темы.

== Description ==

PF Filter не диктует внешний вид карточек товаров, сетки или фильтров — вся разметка остаётся полностью на стороне темы/верстальщика.
Плагин находит разметку по атрибутам `pf-*`, строит фасетный фильтр (чекбоксы, радио, теги, дропдауны, диапазон цены, дерево категорий),
запускает AJAX-запросы к REST API и обновляет список товаров, счётчики, пагинацию и активные фильтры без перезагрузки страницы.

Первая загрузка страницы рендерится стандартным WordPress/WooCommerce loop — плагин не вмешивается в первичный рендер.

Полное описание атрибутов, REST API и структуры конфигурации — см. техническую спецификацию проекта.

== Installation ==

1. Загрузите папку `pf-filter` в `/wp-content/plugins/`.
2. Активируйте плагин через меню «Плагины» в WordPress.
3. Убедитесь что WooCommerce активен.
4. Настройте группы фильтров и сортировку на странице Настройки → PF Filter.
5. Разметьте страницу каталога атрибутами `pf-form`, `pf-target`, `pf-list`, `pf-output`, `pf-templates` и т.д.

= 1.5.8 =
* Критическое исправление: после снятия любого фильтра (чекбокс, метка, категория и т.п.) список товаров и счётчик могли остаться неверными («залипшая» фильтрация), если до этого границы цены автоматически сузились под тот фильтр (например, у выбранного цвета в наличии только один товар по одной цене). Причина — collectFilters() всегда отправлял текущий диапазон цены как активный фильтр, даже когда это было чисто визуальное автоподстроенное значение, а не выбор пользователя; после снятия другого фильтра суженная цена продолжала «приклеенной» лететь в запрос и реально фильтровала товары.
* Ползунок цены теперь помечается data-user-adjusted только реальным действием пользователя (drag/клавиши/числовое поле) — автоматическая подстройка границ под другие активные фильтры (см. 1.5.5) этот флаг не трогает. Фильтр price отправляется на сервер только если флаг стоит; сброс группы/всех фильтров его снимает.

= 1.5.7 =
* Исправлено: при схлопнувшемся диапазоне цены (min === max — очень узкий диапазон или один товар) оба ползунка накладывались друг на друга в одной точке (0%), не различить и не за что зацепиться. Теперь в этом случае min-ползунок раскладывается на 0%, max — на 100%, оба остаются на виду.
* [pf-filter-remove] теперь скрыт по умолчанию — виден только когда у этой конкретной группы реально есть активный фильтр (как и [pf-active-reset]).
* Критическое исправление: клик на [pf-filter-remove] визуально сбрасывал фильтр и пересчитывал счётчики, но список товаров обновлялся только после второго клика (заметно на пагинации в режиме both/load-more/infinite). Причина — forceReplace/silent были общими полями на инстансе, выставлялись в момент вызова runFilter(), но читались в handleResponse() асинхронно в момент ответа; если между вызовом и ответом успевал выполниться другой runFilter() (например, отложенный rangeDebounced), ответ читал уже перезаписанные чужие флаги. Теперь эти флаги передаются per-request явно вместе с ответом, а не через общее состояние.

= 1.5.6 =
* Критическое исправление регрессии 1.5.5: границы ползунка цены схлопывались в цену одного товара (data-min == data-max) уже при первой загрузке страницы, дальше ломая фильтрацию по всем остальным запросам. Причина — PF_Query::build() прогонял posts_per_page через absint(), которая отбрасывает знак: -1 (конвенция WordPress "без ограничения", так вызывает count_price_bounds(), чтобы посчитать реальный min/max по всем подходящим товарам) превращался в 1 — запрос молча ограничивался одним товаром. Раньше баг был спящим, клиент counts.price просто игнорировал; проявился сразу после того, как в 1.5.5 подключилась подстройка границ.

= 1.5.5 =
* Новое: ползунок цены теперь подстраивает границы трека (не только текущий выбор) под остальные активные фильтры — точно так же, как уже подстраиваются счётчики у остальных групп. Сервер это уже считал (counts.price), клиент раньше данные игнорировал. Если ползунок ещё не трогали — граница "едет" вместе с новыми доступными min/max; если уже выбран поддиапазон — он обрезается по новым границам, а не сбрасывается.
* Новое: атрибут [pf-filter-remove] — необязательная кнопка сброса фильтра конкретно одной группы (в отличие от [pf-active-reset], сбрасывающего все фильтры разом), может быть где угодно внутри pf-template, работает одинаково для любого шаблона группы.
* Новое: страница настроек предупреждает ⚠, если для включённой настройки в реальной вёрстке нет нужного элемента — "Показывать счётчик товаров" (нет [pf-filter-count]), вкладка "Сортировка" (нет [pf-sort]), группа → "Поиск" (нет текстового поля в шаблоне), группа → "Цвета" (нет [pf-filter-swatch] в шаблоне).
* Исправлено: при сбросе диапазона цены (Сбросить все фильтры / кнопка сброса группы) ползунок возвращался в позицию без центрирования (левый край на 0%/100% вместо центра) — не использовал фикс центрирования из 1.5.3.
* Внутренний рефакторинг: resetGroupFilter() раньше сбрасывал только range-группы (использовался лишь чипом цены) — для checkbox/radio/tags/category-tree ничего не делал. Общая логика сброса вынесена в resetGroupControls(), теперь работает для всех типов групп (нужно было для [pf-filter-remove]).

= 1.5.4 =
* Критическое исправление регрессии 1.5.3: поиск внутри группы фильтра (в т.ч. по категориям) переставал работать вообще. Причина — reinitWebflow() вызывал общий Webflow.destroy()+Webflow.ready(), который перезапускает ВСЕ модули Webflow разом, включая "forms" — тот управляет той же <form>, что и pf-form, и его переинициализация ломала обработчик поля поиска.
* reinitWebflow() переписан точечно: вместо общего destroy()+ready() теперь вызывается только Webflow.require('dropdown').ready() (безопасно вызывать повторно — модуль сам снимает старые обработчики перед новыми) и Webflow.require('ix2').init(). Модуль "forms" (и другие, отвечающие за не относящуюся к дропдаунам функциональность) больше не трогается.
* Дополнительная защита: обработчик поиска внутри группы теперь навешивается делегированно на весь узел группы, а не напрямую на поле ввода — устойчиво к любой переинициализации поля сторонним JS темы, не только Webflow.

= 1.5.3 =
* Исправлено: ползунок диапазона цены визуально вылезал за пределы трека справа. positionHandle() ставил только left:X% (левый край ползунка), без компенсации его собственной ширины — на 100% ползунок неизбежно вылезал наружу. Добавлен transform: translateX(-50%), теперь ползунок центрируется на своей позиции.
* Исправлено: вложенные категории не находились при поиске по дереву категорий. Строка-родитель со своим pf-hidden визуально скрывала всех потомков (display:none у предка перекрывает детей), даже если у самого совпавшего потомка pf-hidden был снят. Строка теперь видна, если совпала она сама, либо любой её потомок/предок в цепочке.
* Исправлено: «Сбросить все фильтры» не снимал визуальное выделение с активной радиокнопки. У Webflow-виджета радио «визуально отмечен» — отдельный CSS-класс (w--redirected-checked) на соседнем элементе, управляемый только по клику на конкретный input; кликом принципиально нельзя выразить «сними выбор со всех» (радио — это всегда «выбери этот один»). Теперь при программном снятии класс убирается явно.
* Исправлено: вложенные дропдауны дерева категорий не раскрывались по клику после того, как их строил плагин (хотя в самой теме, без плагина, работали). Причина — Webflow инициализирует свои дропдауны один раз при загрузке страницы, а дерево категорий строится позже, асинхронно после ответа /config, поэтому клонированные узлы дерева Webflow просто не видел при своей инициализации (в отличие от групп верхнего уровня, тут нельзя один раз «переместить» оригинал — категорий на одном уровне обычно несколько). Добавлен вызов Webflow.destroy()/Webflow.ready()/require('ix2').init() сразу после построения групп — просит сам Webflow пересканировать DOM и переинициализировать свои дропдауны/анимации как есть, никакой собственной логики раскрытия плагин не реализует. На сайтах без Webflow (window.Webflow не существует) — no-op.

= 1.5.2 =
* Исправлено: переход по ссылке в каноничном для WordPress формате пагинации `/page/N/` (например `/shop/page/3/?price_min=...`) открывал страницу 1 вместо N. Плагин читал номер страницы только из query-строки (`?paged=N`, в этом формате он сам пишет URL), но не из сегмента пути `/page/N/`, в котором отдаёт ссылки сам WordPress/тема. Теперь читается и то, и другое; `updateUrl()` при этом убирает сегмент `/page/N/` из пути, чтобы не задваивать номер страницы одновременно в пути и в query-строке.
* Исправлено: группы фильтра, нерелевантные текущей выборке (например, после выбора категории, где ни у одного товара нет значений по этому атрибуту), не скрывались автоматически — оставались видны со старыми значениями. Сервер уже пересчитывал релевантность на каждый AJAX-запрос (авто-релевантность по категории и по остальным активным фильтрам), но клиент использовал это только для обновления цифр счётчиков, не для показа/скрытия самой группы.
* Исправлено: клик по строке-тегу (шаблон tags, в т.ч. плоский список категорий) и ещё несколько кликов внутри формы (сортировка, «Загрузить ещё», «Сбросить все фильтры», удаление чипа активного фильтра) не вызывали preventDefault. Если верстальщик использовал для такого элемента `<button>` (тип по умолчанию submit), клик реально отправлял [pf-form] как обычную HTML-форму — на Webflow-сайтах это показывало служебную ошибку самого Webflow вида «Ошибка отправки! Формы не настроены». Добавлена и точечная защита в каждом обработчике, и общий preventDefault на submit самой формы (она никогда не должна отправляться нативно).
* Исправлено: пагинация по страницам (одинокая кнопка «1») не скрывалась, когда весь результат умещается на одну страницу — теперь блок номеров страниц скрывается целиком, если страница всего одна.
* Исправлено: в таблице групп фильтров содержимое ячеек «Range: шаг/ед.», «Дерево: глубина», «Цвета» съезжало под чужие заголовки. Причина — CSS скрывал неприменимые к шаблону ячейки через `display:none`, а у разных строк скрыт разный набор из этих ячеек, из-за чего оставшиеся видимые в каждой строке сдвигались на разное число столбцов. Заменено на `visibility:hidden` — ячейка остаётся зарезервированным столбцом, выравнивание больше не ломается.
* Новое: настройка «Сортировка значений» для каждой группы фильтра — по алфавиту (А→Я/Я→А) или по количеству товаров (по возрастанию/убыванию). Работает для любого типа группы со списком значений (таксономия, кастомный атрибут, плоские категории, дерево категорий — там сортировка применяется на каждом уровне отдельно).
* Новое: фильтрация по меткам товара (product_tag) — раньше поле было недоступно ни для выбора в админке, ни в самом построителе AJAX-запроса (даже если группу как-то настроить руками, реальная фильтрация по ней молча не срабатывала бы).
* Названия шаблонов («checkbox», «radio», «tags» и т.д.) в выпадающем списке «Шаблон» на странице настроек переведены на русский — само значение pf-template в разметке темы не меняется, только подпись в админке.
* Исправлено: при «Сбросить все фильтры» радиокнопки не сбрасывались визуально (чекбоксы и теги — сбрасывались). Программный сброс слал только событие change; часть кастомных Webflow radio-виджетов синхронизирует визуал по click, а не по change — теперь рассылаются оба события.

= 1.4.1 =
* Критическое исправление: сайт (админка и фронт) полностью белел после обновления до 1.4.0. Причина — в class-pf-card-template.php однострочный комментарий содержал буквальный текст `<?php ... ?>`; PHP обрывает такой комментарий на первом `?>` и переходит в текстовый режим, а последующий `<?php` в файле включал PHP обратно посреди обычного текста комментария — из-за этого весь код в файле дальше по тексту не парсился (`Parse error: syntax error, unexpected identifier`). Комментарий переписан без буквальных PHP-тегов внутри. Ошибка воспроизведена и исправление подтверждено реальным PHP-линтером (php -l) на PHP 8.5, а не подсчётом скобок вручную.

= 1.3.0 =
* Новое: автоматическое извлечение шаблона карточки товара прямо из PHP-файла страницы каталога (PF_Card_Template) — без ручного создания content-product.php и без каких-либо pf-* атрибутов внутри карточки.
  Плагин находит PHP-файл, которым тема рендерит конкретную страницу (кастомный page template или переопределение архива WooCommerce), вырезает из него тело цикла товаров внутри [pf-list] (код между the_post() и endwhile) и подключает его один раз на каждый товар при AJAX-фильтрации — включая условные блоки темы (бейджи, атрибуты и т.п. отрабатывают их же собственной логикой, а не угадыванием).
  Результат кэшируется в wp-content/uploads/pf-filter-cache и пересчитывается автоматически при изменении файла темы. При любой ошибке извлечения/выполнения — тихий откат на прежний wc_get_template_part('content','product').
* Диагностика: новая проверка, использовался ли автоматически извлечённый шаблон карточки для указанной страницы.
